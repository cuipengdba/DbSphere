# 规模采集与历史可靠性验收

## v2.6 运行状态

管理员进入系统设置的采集状态，可按组织和 Linux、Kubernetes、托管数据库或 MySQL 采集来源查看最近一次调度的排队、目标查询和 PG18 写入耗时 P95。新鲜度按每个资产最近一次成功的自动采样计算，默认窗口为两个采集周期。缺少耗时的数据保留为待采样。队列可查看隔离、退避、租约与最后一次原始采样。

- 排队耗时由 PG18 的租约领取时间减去任务截止时间计算。目标耗时包含连接和目标查询。PG18 写入耗时从进入写入函数到任务状态更新前，包含获取连接、写入样本、告警和证据 SQL。
- 配置两个或更多工作位时，每副本预留一个隔离工作位。目标采集阶段达到 5 秒、或者连续失败两次后进入隔离队列。及时成功后回到常规队列。单工作位按到期顺序执行。接管使用原到期时间和新租约，过期副本无法写入重复样本。
- 小时趋势保留已完成的汇总，只重读有迟到样本的相邻时段。小时表仍生效期间，原始数据清理保留同小时的最后样本和已记录的最大阻塞证据。事件优先按样本 ID 和采样时间定位分区，旧记录和跨时点基线仍可通过 ID 查询。至少两个周期的采样间隔会在后续样本中记录，有对应事件时可直接查看。

## 复测方法

在测试环境中准备独立 PG18 监控库、两个运行相同 DbSphere 版本的 Linux 副本，以及至少三台真实 PostgreSQL 目标。副本使用同一个监控库和主密钥，将 `DBSPHERE_ENABLE_GO_COLLECTOR` 设为 `true`、`DBSPHERE_COLLECT_INTERVAL_SECONDS` 设为 `30`。目标安装 `pg_stat_statements` 并为本次演练新建专用只读监控角色。Docker 用于复测时直接读取测试库计数器，正式部署仍可用标准或增强一键离线包。

在可以访问控制台与 Docker 主机的电脑上准备如下配置。脚本默认运行 100 个纳管资产、30 秒采集、8 小时。为并行验证镜像或复核局部问题可调整 `durationSeconds`。同一目标可能承载多个纳管资产，报告分别记录资产数量与目标实例。

```json
{
  "site": "http://127.0.0.1:18090",
  "storeContainer": "dbsphere-load-history",
  "monitorUser": "dbsphere_collector",
  "assetCount": 100,
  "intervalSeconds": 30,
  "durationSeconds": 28800,
  "report": "/tmp/dbsphere-load.json",
  "targets": [
    { "host": "load-pg14", "container": "load-pg14" },
    { "host": "load-pg16", "container": "load-pg16" },
    { "host": "load-pg18", "container": "load-pg18" }
  ]
}
```

为复测进程设置 `DBSPHERE_LOAD_ADMIN_PASSWORD` 与 `DBSPHERE_LOAD_MONITOR_PASSWORD`，运行 `node scripts/drill-collector-load.mjs load.json`。脚本创建有相同批次前缀的测试资产，预热后记录每个资产的调度相位。健康覆盖率按期望时刻与成功落库的唯一时刻核对。报告还保留重复计数、采集副本、目标侧 SQL 次数与耗时、PG18 数据库大小变化和 API 实测延迟。

将一个独立目标暂停，并另纳管一个连接会被拒绝的测试端点，观察它们离开常规队列。在暂停目标占有租约时中断拥有该租约的测试副本，检查同一资产与原到期时间仅有一份新副本采样。独立暂停监控 PG18 超过两个周期，恢复后检查原事件、原始证据、缺口及关闭事件的样本。建议在负载区间和存储故障区间分别记录指标，以便核对两类条件下的结果。

本版本的实际运行条件和负载结果随 [v2.6.0 发行说明](https://github.com/cuipengdba/DbSphere/releases/tag/v2.6.0) 公布。

## 早期基准记录

> 2026-11-19 开发版负载冒烟。测试仅使用本机隔离的 PostgreSQL 14 容器目标与独立 PG18 监控库，不代表生产规模或不同目标实例的资源开销。

## 场景

在测试监控库中复制一个已验证的托管模式资产连接配置，创建 20 个一次性资产，均指向同一个 PG14 测试容器。以 `DBSPHERE_ENABLE_GO_COLLECTOR=true`、15 秒周期和 4 个工作进程启动当前 Go 静态程序。目标连接使用 PostgreSQL 只读会话设置；测试资产的登录角色是隔离容器中的 `postgres`，因此此轮不能证明最小权限账号的性能。

| 轮次 | 资产 | 成功样本 | 失败样本 | 首末样本写入时间差 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 20 | 20 | 0 | 0.66 秒 |
| 2 | 20 | 20 | 0 | 0.85 秒 |

两轮样本均识别 PG14，且没有 Linux/K8S 基础设施指标。第一轮从创建资产到最后一个样本落库约 19.68 秒，包含进程启动和调度等待，不能当作纯采集耗时。测试结束后停止 Go 进程，删除全部 20 个一次性资产及其样本，原有托管模式验收资产保留。

测试证明该夹具下工作队列可以完整处理 20 个到期资产而不漏采。它没有测量 CPU、内存、目标数据库 SQL 代价、网络时延、不同服务版本的权限差异或 PG18 长期写入成本；多个 DbSphere 副本同时采集仍需租约设计。V1.0 的采集开销与规模门槛保持开放。
