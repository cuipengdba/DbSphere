# DbSphere v2.0 开发规划

## 版本目标

为容器化 PostgreSQL 增加独立的「容器磁盘 I/O 与文件缓存」专题。实时监控能定位异常对象，历史分析能回放异常和恢复过程，Grafana 专项能沿同一资产和时间窗继续下钻。一次故障沿用一个事件 ID，串起 PostgreSQL、容器、节点与存储的证据。

开发基线为 v1.50.0。复用现有 Kubernetes 资产发现、Linux 指标、PVC 用量、采集能力状态、实时推送、PostgreSQL 18 历史存储、事件证据和 Grafana 登录代理。继续支持 Linux 裸机部署及 Linux 上的 Docker 和 Kubernetes 目标，监控 PostgreSQL 14–18。服务端使用 Go，前端为静态页面和 HTTP API。默认浅色，可切换深色，继续提供标准与增强一键离线包。原生监控、历史和规则诊断可独立运行，AI 接入可选。

## 观测数据与归属

| 层级 | v2.0 指标 | 口径与来源 |
| --- | --- | --- |
| PostgreSQL 容器 | 读写 B/s、读写 IOPS、设备排行、I/O PSI，具备证据时展示 I/O 限流 | cgroup v2 `io.stat` 按设备 `major:minor` 读取累计字节数和操作数，按有效采样间隔计算速率。`io.pressure` 表示等待压力。限流来自可读且已关联的控制器配置或运行时证据。 |
| 文件页缓存 | `active_file`、`inactive_file` 当前值、变化量和趋势，联看 `file`、`file_dirty`、`file_writeback`、`workingset_refault_file`、内存压力和回收 | 取 `memory.stat` 与可用的 `memory.pressure`、`memory.events`。两项文件缓存按字节独立画线。`file` 单独展示，避免将两条 LRU 列表相加作为总缓存。单独的 `inactive_file` 下降只触发观察。 |
| 节点与卷 | 节点设备平均等待、吞吐量、队列与忙碌度，PVC 容量与健康，受支持来源提供的卷级 I/O | 明确标记节点设备、容器块设备和 PVC 的数据层级。仅有挂载关系时显示对应的卷与设备证据。共享卷、网络存储或无法确定设备的场景保留节点和容量指标，并提示卷级 I/O 的可用情况。 |
| PostgreSQL | I/O 等待、区间块读取和缓冲命中、WAL、检查点、临时文件、相关 Top SQL。PG16–18 增补可用的 `pg_stat_io` | 兼容 PG14–15 的采集视图，按版本和权限探测。I/O 计时关闭时标明该项状态。数据库层观测和操作系统块设备指标各自保留采样范围。 |

采集首选 Linux cgroup v2。已有可信的 Prometheus 采集侧和只读节点采集均可接入。Kubernetes 复用现有对象发现，节点采集增量通过离线 DaemonSet 分发。Docker 可关联已登记的采集源，首次接入时提供数据库资产与容器的一次绑定。cgroup v1 首批验证可读取的 `memory.stat` 和 `blkio` 子集，明确缺失的压力指标。按运行时和真实验收结果公布支持矩阵。部署控制台无需挂载 Docker Socket，节点和 Kubernetes 采集权限随离线包说明。 [Linux cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html) · [Kubernetes 节点指标](https://kubernetes.io/docs/reference/instrumentation/node-metrics/) · [PostgreSQL 16 监控统计](https://www.postgresql.org/docs/16/monitoring-stats.html)

- 身份绑定使用环境或集群、数据库资产、容器实例标识和生效区间。Kubernetes 使用 Pod UID 和容器 ID，关联工作负载、节点与 PVC。Docker 使用主机 ID 和完整容器 ID。多容器 Pod 默认聚焦 PostgreSQL 容器，可切换查看 sidecar。容器重启和 Pod 迁移标注为事件，旧实例指标仍可回放。
- 每条证据带采样时间、来源、层级和质量状态。首个样本、计数器重置与采样中断切断速率曲线。未纳管、权限不足、指标缺失、数据过期分别显示原因，缺值保留为空。
- I/O 字节数和操作数是累计计数，缓存大小是瞬时值。设备延迟使用可核验的来源和统计口径，百分位仅在具备相应分布数据时提供。

## 原生页面与 Grafana

**实时监控 → 容器磁盘 I/O 与文件缓存。** 资产列表标示运行环境。进入容器化数据库后，顶部可选容器、节点、设备和时间范围，展示读写吞吐、IOPS、活动和非活动文件缓存及 I/O 压力。两个联动主图展示读写活动和缓存变化，下方将 PostgreSQL 等待、PVC 和节点设备对齐。右侧定位异常时间、对象、数据来源及异常证据。无指标时，在相应图表位置提供采集状态和接入入口。

**历史分析 → 容器磁盘 I/O 与文件缓存。** 支持快速时间范围、自定义时间窗、两个时段对比、同步游标、异常区间缩放、重启及变更标记。历史明细与聚合沿用 PG18 存储和已有保留期配置，保存峰值及有效样本覆盖。原生历史可查询超出 Prometheus 保留期的时段。事件内保存证据引用及关键区间摘要，供事后回放和复核。

**实时指挥大盘。** 提供独立全屏模式，支持 1080p 展示和浏览器窄窗口自适应排版。顶部给出健康资产、异常实例、当前告警及数据更新时间。中央使用联动曲线和按容器或设备的颜色矩阵定位热点，右侧给出异常排行和 RCA 入口，底部时间带记录重启、发布和告警。浅色与深色共用读、写、缓存、压力配色和单位，异常状态同时有文字或图标。停止更新时保留最后采样时间，动画用于数据更新与告警状态转换，并尊重系统减少动态效果的设置。

| Grafana 专项 | 首屏与下钻 |
| --- | --- |
| PostgreSQL 容器磁盘 I/O | 读写吞吐、IOPS、I/O PSI、设备热点矩阵，点选设备进入节点与卷分析。 |
| 文件缓存与内存回收 | 双曲线展示 `active_file` 和 `inactive_file`，叠加 refault、dirty/writeback、内存压力及回收时间线。 |
| Kubernetes 节点与存储卷 | 工作负载 → Pod → 容器 → Node/PVC 联动，显示容量与健康、节点设备等待、具备数据来源的卷级指标。 |
| PostgreSQL 存储等待与根因 | I/O 等待、WAL/检查点、临时文件、可用的 I/O 计时、相关 SQL，以及原事件和历史时间窗链接。 |

沿用现有 Grafana 访问授权和统一登录。出入原生页面、事件及 Grafana 时传递资产、容器、起止时间和事件 ID。Grafana 看板、变量、数据源及记录规则随增强离线包预置，使用稳定的看板 UID。 [Grafana 配置预置](https://grafana.com/docs/grafana/latest/administration/provisioning/) · [Grafana Prometheus 数据源](https://grafana.com/docs/grafana/latest/datasources/prometheus/)

## 一次故障的证据链

演练场景为「某 PostgreSQL 实例读查询变慢」。进入事件后，先定位 PostgreSQL 的 I/O 等待、受影响的 SQL 和起始时间，再对齐容器的文件缓存下降、refault 升高和块读增多，最后检查 I/O PSI、节点设备等待及 PVC 归属。规则综合这些证据给出「文件缓存回收引发重读」或「底层存储拥塞」等候选，列出证据、有冲突的信号及缺失的数据点。恢复后，在同一事件中比较等待、refault 和块读是否回落。

首批覆盖缓存回收伴随重读、持续写回压力、已验证的容器 I/O 限流和共享设备拥塞。只有缓存下降或 PVC 用量变化时，保留对应观测并将根因标为待确认。规则输出可进入告警、事件和历史复盘，模型接入后可基于同一证据解释和总结。

## 开发任务及顺序

- [ ] **2.0-01 指标契约与身份。** 固定单位、类型、来源、标识和质量状态，建立容器实例有效期及设备/PVC 映射，覆盖重启、改名、迁移、时钟偏差和多容器 Pod。
- [ ] **2.0-02 采集与健康状态。** 交付只读 cgroup 采集和已有 Prometheus 源适配，提供 Kubernetes DaemonSet 及 Docker 接入说明。按源去重，处理权限不足和限时重试，量化采集开销。
- [ ] **2.0-03 数据写入与历史。** 按现有迁移机制扩展 PG18 历史，补齐速率、保峰降采样和覆盖判定。推进正常查询、长窗口查询和既有资产升级回归。
- [ ] **2.0-04 原生实时、历史和指挥大盘。** 实现专题路由、两种主题、全屏、统一区间、状态设计和关键对象下钻。
- [ ] **2.0-05 Grafana 专项。** 实现四块预置看板、公共变量、数据链接、记录规则及角色访问回归，验证断网环境下的看板访问和查询。
- [ ] **2.0-06 故障规则与证据回放。** 完成四类诊断规则、事件去重、置信依据、恢复验证及误报回归，使实时、历史和 Grafana 都可回到原事件。
- [ ] **2.0-07 离线升级、回滚及发布。** 将收集端分发文件、镜像和看板写入离线包及清单。验证 v1.50.0 至 v2.0.0 就地升级、备份恢复与按文档回退，发布制品、校验和及支持矩阵。

## v2.0 发布验收

- PG14、15、16、17、18 都运行实际采集和 SQL 兼容测试。Linux 裸机回归，Linux Docker 和 Kubernetes 容器各跑通全链路，Kubernetes 至少覆盖一个带 PVC 的 StatefulSet 和一个 PostgreSQL 加 sidecar 的 Pod。cgroup v1 和受限权限回归单独记录覆盖结果。
- 使用隔离的测试容器和卷产生受控读写、缓存回收和写回压力。核对采集值与原始 cgroup 指标，验证容器重启、计数器重置、指标中断和卷映射不确定场景。实时默认目标为 10 秒采样，变化在正常负载下 30 秒内可见。上线前公布实测采样延迟和开销。
- 从实时大盘异常卡片点击进入事件，复核数据库等待、容器缓存、设备和 PVC 的来源与关联。验证历史和 Grafana 链接保留同一事件、资产和时间窗，回放峰值并验证恢复。切断 Grafana、Prometheus 或 AI 接入后分别验证已有原生采集源支持的监控与 RCA。
- 在阻断外网的 Linux 测试环境验证一键安装、看板预置、镜像和校验和、现有资产与历史的升级保留、失败回退与备份恢复。两种主题下检查全屏大盘、常用浏览器窗口和真实数据展示。

## 2.x 到 3.0 的衔接

- `v2.0.0` 为当前开发和正式发布的唯一版本。该版发布并核验后，等待项目负责人明确 `v2.1.0` 的功能范围。后续按 `v2.1.0` 至 `v2.30.0` 逐小版本开发、测试和正式发布。
- `v2.30.0` 正式发布并核验发布页、制品与升级验收后，在同一发布流程中转入 v3.0 规划。先汇总 2.x 用户反馈、实际产物、运维数据、兼容风险和待完成事项，再输出 3.0 功能边界、后续版本路线图和开发任务 Markdown。
