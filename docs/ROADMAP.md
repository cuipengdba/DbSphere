# DbSphere V0.1–V1.0 十版本功能路线图

> 2026-11-17 修订。十个版本是 **V0.1、V0.2、V0.3、V0.4、V0.5、V0.6、V0.7、V0.8、V0.9、V1.0**。开发已启动；仅完成验收的版本才标记为发布。详见[开发任务清单](DEVELOPMENT_TASKS.md)。

## 目标与依赖

**所有十个版本继承四项硬约束**：支持 PostgreSQL 14–18；被监控的主机操作系统为 Linux；PostgreSQL 可运行在 Linux 主机或 Kubernetes；平台是浏览器/服务器（B/S）架构，服务端部署在 Linux 或 Linux 容器中。新增交付约束：提供容器化一键部署；长期监控数据使用独立的 PostgreSQL 18 数据库。新增 V0.6 起的离线交付：Linux 一键离线包内含预构建 DbSphere 与 PG18 镜像，目标机无需联网、Node.js 或包管理器，但需预装 Docker Engine/Compose；另提供可使用现有 Node.js 24 和外部 PG18 的轻量离线方式。V1.0 必须完成断网安装、升级和回滚验收，单文件可执行程序仅在实际构建与验证后宣称支持。V0.1 的 SQLite 仅是早期样例存储，V0.2 引入 PG18 后才提供长期监控数据保留。PG14 虽已到上游 EOL，仍纳入监控兼容与回归矩阵，并在界面提示升级风险。不同采集层的能力逐版增加，早期版本不宣称已经实现后期的深度功能。

V1.0 完成 PostgreSQL 运维监控闭环：纳管、监控、告警、巡检、SQL/锁/等待分析、应用到数据库的链路关联、Linux/K8S 基础设施关联、证据化根因分析、处置与复盘。**一个问题对应一个事件 ID、一条跨层证据时间线和一组可审查根因候选**。AI 是可选的诊断助手；任何版本的核心链路均不以模型为前提。云 PostgreSQL 以权限允许的信号为准。

| --- | --- | --- | --- |
| **V0.1** | B/S 底座与基础纳管 | Linux 服务端与浏览器控制台；PG14–18 版本识别、只读连接、资产模型；Linux/K8S 运行位置字段及 K8S Pod/实例映射基础；可用性、连接、事务和复制基础指标；事件 ID/证据模型 | 在浏览器纳管 Linux PG 与 K8S PG，五个 PG 大版本连接测试通过；采集失联显示缺失，初始事件可追溯 |
| **V0.2** | PG、Linux 与 K8S 监控纵深 | 会话/等待/锁、WAL、autovacuum、容量增长；Linux 资源；K8S Namespace/StatefulSet/Pod/Container/Node/PVC 资源和事件；PgBouncer 可选采集；PG18 持久化后端；Docker Compose 一键启动 | 从实例下钻到 Linux 主机或 K8S Pod/Node/PVC；缺少权限或采集器时显示能力缺口；一条命令启动 DbSphere 与独立 PG18，重启后样本/事件不丢失 |

| **V0.5** | SQL 性能洞察 | `pg_stat_statements` 可选接入、SQL 指纹、慢 SQL 日志、执行计划快照、Top SQL 与退化对比；关联实例所在 Linux/K8S 资源 | 五个 PG 大版本均能显示可用的 SQL 信号；同一退化问题可关联 SQL、实例和资源时间线 |
| **V0.6** | 跨层根因分析与离线交付 | 锁阻塞图、等待关联、确定性诊断规则和证据图；覆盖连接耗尽、锁链、慢 SQL、复制延迟、磁盘/WAL、autovacuum、K8S OOMKilled 与 PVC 压力；Linux 预构建镜像离线包与一键启动 | 一个问题的事件页展示根因候选、证据、反证和缺失信号；八类故障演练可审查，无法定位时明确说明；断网一键部署通过 |
| **V0.7** | 应用到数据库全链路 | OTel 应用 Trace 接入；服务/请求 → 连接池 → SQL → PG 实例 → Linux 或 K8S Pod/Node/PVC 的关联；拓扑和影响面 | 从示例应用慢请求进入同一事件并追至数据库和运行环境；无 Trace 时明确降级为数据库侧链路 |
| **V0.8** | 可选 AI 分析与预警 | 本地/兼容 API 模型、脱敏证据包、事件摘要、解释型问答、趋势风险建议；模型超时/预算/审计与规则回退 | 关闭模型后 PG14–18、Linux、K8S 的监控与全链路规则诊断照常运行；AI 答案引用证据 |
| **V0.9** | 运维治理与协同 | B/S 控制台 RBAC、工单/审批/审计、受控低风险操作、变更关联和复盘；K8S 权限最小化与操作边界 | 只读用户不能执行操作；审批动作全程可追溯；事件从首次告警、根因到恢复形成闭环 |

## 三条贯穿版本的交付线

1. **非 AI 主干**：从 V0.1 起，监控与告警使用确定性采集和规则。V0.6 根因候选也是可解释规则。AI 只在 V0.8 加入，且能关闭。
2. **采集层级**：数据库连接串提供基础信号；Linux 主机、K8S API/指标/事件、连接池、Patroni、备份依赖相应采集；应用全链路依赖 OTel。每版都公布该版本的信号覆盖表。
3. **安全与可运维性**：从 V0.1 起默认只读、采集自监控与脱敏；V0.9 加入受控处置；V1.0 才按稳定性和兼容性门槛标记正式版。
4. **部署与存储**：V0.1 供开发预览；V0.2 起 Docker Compose 一键启动 DbSphere + 独立 PG18，并允许连接外部 PG18；监控数据与被监控业务库隔离。后续逐版补齐迁移、保留期、备份恢复、容量和升级验证。

## V1.0 之后的候选方向（不属于十版本承诺）

MySQL/其他数据库适配、跨引擎统一事件模型、更广泛的云厂商集成、复杂变更自动化、备份执行编排与高级内核观测。是否实施以 V1.0 用户反馈和维护成本评估为准。
