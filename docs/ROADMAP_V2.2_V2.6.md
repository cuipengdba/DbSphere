# DbSphere v2.2–v2.6 开发规划

以 v2.1.0 为基线。五个版本各有一个主题，按开发、实库测试、离线验收、正式发布的顺序交付。以下任务待开发。2.x 在 v2.30.0 正式发布后转入 v3.0 规划。

| 版本 | 主题 | 值班人员可以完成的事 |
| --- | --- | --- |
| v2.2.0 | 纳管体检与采集覆盖 | 接入时就知道哪些指标能采、哪里缺权限、该由谁处理。 |
| v2.3.0 | 事件调查工作台 | 打开一个告警，沿同一时间窗看影响范围、阻塞链、原始证据和恢复。 |
| v2.4.0 | 容器存储归因 | 定位慢查询与文件缓存重读、设备拥塞或卷容量风险之间的关系。 |
| v2.5.0 | 应用连接超时诊断 | 看出连接是在应用池、PgBouncer、建连阶段还是数据库执行阶段卡住。 |
| v2.6.0 | 规模采集与历史可靠性 | 大批实例连续采集时，能发现积压、隔离慢目标，并回查早期事件。 |

## 共同交付条件

- 监控目标覆盖 PostgreSQL 14–18，继承 v2.1 的 PostgreSQL 19 回归与瀚高安全版 4.5.9 适配。按实测维护 Linux 裸机、Docker 和 Kubernetes 的支持矩阵。瀚高能力按实际版本、权限和现场认证方式展示。[当前支持矩阵](SUPPORT_MATRIX.md) · [瀚高接入](HIGHGO.md)
- Go 后端、静态页面和 HTTP API，默认浅色并支持深色。独立 PostgreSQL 18 保存监控历史、事件及证据。无模型时可完成纳管、采集、告警和规则诊断，模型接入后可引用原事件的脱敏证据。
- 每版至少一项真实故障演练贯穿发现、影响范围、根因候选、原始证据和恢复，沿用同一个事件 ID。标明数据缺失、时间偏差、身份歧义和权限不足。恢复须有新的有效观测支持。
- 每版发布 Linux amd64 和 arm64 静态程序、标准与增强一键离线包及原生 systemd 包。断网验证安装、前一正式版升级、按文档回退及 PG18 数据保留。增强包验收预置 Grafana 与 Prometheus，标准包验收原生工作台。发布时核对版本徽标、支持矩阵、制品 SHA-256 和验收记录。

## v2.2.0 纳管体检与采集覆盖

- [ ] **22-01** 将纳管预检和资产采集能力合并成一份可复查报告。按目标引擎和部署环境分别核对连通、认证、已配置的 TLS 校验、只读会话、统计视图及扩展。对已接入的 Linux、K8S 和容器采集源显示可见范围与最后采样时间。
- [ ] **22-02** 在资产列表增加按失败原因分组和批量复检。对同一资产对照上次结果，说明能力变化、受影响的诊断和可查证的处理入口。权限校验使用专用只读账号，复检沿用原资产 ID。
- [ ] **22-03** 让采集失联、权限降级与数据库不可用各自沿用已有事件逻辑。以实测状态区分正常、受限、缺采与不适用。报告和导出仅包含所需的脱敏信息。

**验收**　在 PostgreSQL 和瀚高 4.5.9 测试实例分别撤回会话统计权限，基础连接与样本继续可用，跨会话等待显示受限。权限恢复后复检同一资产，以新样本关闭原采集覆盖事件。另用 K8S 只读账号验证 PVC 权限不足与已取得的数据库数据可独立显示。

## v2.3.0 事件调查工作台

- [ ] **23-01** 重做告警进入后的事件首屏。优先显示受影响的集群、实例、数据库、事件起点和当前状态。左侧可切换数据库、连接池、应用和基础设施，右侧固定根因候选、支持证据、反证及下一步核查入口。
- [ ] **23-02** 在现有事件回放上增加固定的共同游标和故障前、触发、恢复三个对照窗。锁树、等待趋势与原始采样跟随所选时刻。从原生页面、实时大盘和 Grafana 跳转时保持事件、资产和时间范围。
- [ ] **23-03** 将选中的证据和人工结论用于复盘导出。允许从后续采样核对恢复。没有会话 Query ID 的瀚高场景保留 PID 和时间证据，图上标明 SQL 关联的可用性。

**验收**　注入真实 PostgreSQL 锁阻塞，同时制造一个无关的容器波动。事件首屏最多三次点击到达阻塞者原始样本，返回保留时间窗。同窗但身份不符的容器信号不会进入直接证据。释放锁后同一个事件显示恢复。浅色、深色和离线浏览器均可完成全流程。

## v2.4.0 容器存储归因

- [ ] **24-01** 在现有磁盘 I/O 与文件缓存专题补齐设备及卷映射的证据和有效区间。核对 Linux Docker 的容器 ID，以及 K8S 的 Pod UID、容器、Node 和 PVC。共享设备、网络卷或映射冲突显示实际可见范围。
- [ ] **24-02** 为现有存储规则增加分段对照与反证检查。同窗核对 Active/Inactive file、页面重读、设备压力和 PG I/O 等待。另展示卷容量余量和有充分历史覆盖时的耗尽估算。容器重启、缺采和计数器重置切断增量。
- [ ] **24-03** 在原生专题和 Grafana 存储看板提供以异常设备或卷为入口的下钻。回到原事件时展示缓存、设备、数据库等待的前后变化及恢复样本。[现有容器专题](CONTAINER_STORAGE.md)

**验收**　在 Linux Docker 和带 PVC 的 Kubernetes PostgreSQL 上演练可复现的 I/O 异常。分别核对缓存下降伴重读和设备排队的证据，并验证只有缓存下降或共享卷归属不明时不会确认卷级根因。趋势、Grafana 和恢复记录均回到原事件。

## v2.5.0 应用连接超时诊断

- [ ] **25-01** 在现有 OTLP 接入上增加受控的连接阶段数据。分别记录应用池获取、数据库建连、PgBouncer 排队观测和数据库执行时段，并区分该次请求的时长与连接池窗口统计。先验收 Go 示例应用和实际 PgBouncer。
- [ ] **25-02** 按服务、业务端点、数据库和时间证据关联事件。有后端 PID 时复用锁链核验。超时发生在建连前或缺少可靠身份时，展示可证实的阶段，不推定锁阻塞或将请求分配给任意实例。
- [ ] **25-03** 在事件调查页对齐请求异常、连接池队列和数据库等待，提供按服务、失败阶段过滤及脱敏 Trace 链接。未接入应用埋点时按已采到的连接池与数据库证据诊断。[现有请求锁链演练](TRACE_POOLER_INCIDENT.md)

**验收**　用真实 HTTP 请求分别演练应用池耗尽、PgBouncer 排队和 PostgreSQL 锁等待。每次故障的影响、阶段与恢复进入同一个事件。核对无后端 PID、端点歧义、延迟到达的 Span 均能如实显示。

## v2.6.0 规模采集与历史可靠性

- [ ] **26-01** 扩展现有 PG18 采集租约与系统状态。按采集来源和组织显示排队延迟、目标查询耗时、写入耗时及样本新鲜度。限制慢目标持续占用工作节点，并隔离频繁断连的目标。
- [ ] **26-02** 优化高并发采集下的长区间趋势与事件证据读取。验证原样本、小时汇总、峰值链接与事件证据引用在迟到补算、保留期清理和 PG18 重启后的完整性。
- [ ] **26-03** 发布可复跑的多实例负载方案和实测报告。记录机器配置、数据库实例数、资产数、周期、目标侧开销、PG18 磁盘及响应时间。扩大规模前用报告核对容量边界。[当前采集负载记录](COLLECTOR_LOAD_ACCEPTANCE.md) · [历史存储](HISTORY_STORAGE.md)

**验收**　初始试验目标为 100 个资产、30 秒采集、连续 8 小时，使用多个真实目标实例。健康目标有效采样覆盖率目标为 99%，调度延迟 P95 不超过一个采集周期。混入慢目标并重启采集副本，检查快目标覆盖、租约接管和样本去重。短停监控 PG18 后，历史缺口准确可见，原事件证据可查，恢复样本回到原事件。性能数据以报告中的实测条件为准。
